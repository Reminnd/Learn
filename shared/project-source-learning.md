# 真实项目源码映射学习法（Vibe Coding项目适用）

> 这是 Learn Agent 的**按需教学辅助流程**，服务于现有课程的“原理→框架→工程”链条。学习者可以提供正在Vibe Coding的项目供读代码、找范式/函数、追踪调用链。**项目存在或能运行，不意味着代码由学习者手写，也不代表学习者已经掌握。**
>
> 默认只读分析，未经用户明确指示不修改仓库、不运行不可信脚本、不提交代码、不自动创建长期Project Track、不改变章节进度与mastery标准。

## 1. 教学目标

对当前正在学习的**一个**知识点，在学习者提供的真实工程中回答：

1. **为什么存在**：要解决的业务/运行问题和约束是什么？
2. **在哪里**：哪一个文件、类或函数承担这一职责？必须看到真实代码才写定位路径。
3. **如何流转**：入口参数来自哪里？关键函数如何互相调用？返回、状态与异常到哪里？
4. **属于什么范式/模式**：是ReAct、工具调用、Plan-and-Execute、Strategy/Adapter等；证据在哪？还是只有类似名称但实现不同？
5. **替代方案和边界**：如果改用另一个方案，会影响安全性、成本、可测试性、并发、可维护性中的哪些？
6. **能否迁移**：能否在原课程的原理版或另一个语言里复述最小等价流程？

## 2. 单个知识点的默认教学过程（一次只检验一题）

```text
从已经提交的真实学习位置继续
→ 当前章节的一个概念/函数/范式
→ 最小原理和LangChain/LangGraph映射
→ 在用户提供的项目中定位实例（只读，默认不执行）
→ 追踪入口、schema、handler、状态、结果/错误的调用链
→ 对照“原理 ↔ 真实工程 ↔ Python/TypeScript”
→ 分析异常路径和设计取舍
→ 让用户独立解释一个具体问题
→ 根据既有章节验收契约判断下一教学动作
```

- 不要用项目浏览替代原章节的EX/Q&A及mastery门槛。
- 如果当前用户只想看实例，优先追踪1个入口及其直接调用链；不要一次性分析整个工程，更不要强制改造项目。
- 当前章节还没掌握Python/TypeScript对应语法时，老师先解释出现的`Protocol`/`async`/`interface`/`Promise`等必要知识，避免把新语法负担当成Agent范式难度。
- 当用户提出修改/验证练习时，可任选：解释→预测结果→阅读现有测试→写最小测试→在授权后修改极小一处。**手敲代码不是唯一学习途径，但独立理解与证据不可省略。**

## 3. 从项目抽取的最小“源码学习卡”

用一张卡记录，不复制整套项目，也不把AI产出冒充手写：

| 字段 | 该填什么 |
|---|---|
| 当前课程位置 | stage/chapter/section（来自runtime，不从旧聊天猜） |
| 概念或函数 | 例如：Tool Registry、ReAct式循环、Executor Adapter、条件路由 |
| 项目来源 | 用户提供的仓库URL/文件；提交SHA或版本（能取到时） |
| 生成/作者来源 | 学习者说明的Vibe Coding/AI生成/他人贡献/自己手写；未知则标记未知 |
| 源码位置 | 实际核实的文件路径、类/函数、相关测试 |
| 调用路径 | `input → parse/validate → route → execute → result/error → output` |
| 对应范式 | 名称+证据，或“未找到该范式”；不能仅凭文件名判定 |
| 工程问题 | 一个真实失败场景及当前保护机制 |
| 掌握证据 | 自己能解释输入输出、状态变化和选择理由；测试证据要标明由谁执行 |
| 下一练习 | 一个问题或最小验证动作（与原有章节契约对齐） |

**能力记录区分**：

- `seen`：已经定位或看过源码，但未能解释；
- `understood`：可独立解释真实调用链和为什么这样设计；
- `verified`：有明确的运行、测试、断点或日志证据，并注明是谁操作；
- `authored`：有独立编写/更改行为的证据，且通过相应验证。

这些标签只用于源码练习描述，**不替代仓库既有的Learning State、代码能力量表和mastery计算，也不新建持久化状态字段**。AI生成的代码、助手自己跑过的测试只可归入相应来源，绝不直接计为学习者的`authored`或`verified`。

## 4. 一个范例：在TypeScript Gateway中学习Adapter

> 以下是**示意模板**，不是声称某个仓库存在同名函数。具体项目路径与实现必须先读取源码再确定。

- 已知概念：`Strategy/Adapter`通过稳定契约隔离不同执行器。
- 追踪问题：Gateway通过哪个入口接受请求？参数经哪层校验？在哪个函数选择执行器？执行器如何处理超时、取消和结果？失败后由谁转换为HTTP错误或事件？
- Python对照：`Protocol`/抽象类、函数参数验证、异步执行接口。
- TypeScript对照：`interface`、Zod、`Promise`、`AbortSignal`、执行器适配器。
- 问答示例：**为什么Gateway不应该直接拼接命令执行任意模型生成的Python代码？** 让学习者说明隔离边界、执行权限、资源限制及替换性。

遇到动态代码执行时，**不能**用任意代码在宿主机的演示替代安全设计。未满足安全隔离与资源约束时，只使用假执行器、可信固定样例或静态阅读。

## 5. 已提供的开源源码案例与后续项目清单

用户已提供首批6个公开源码参考仓库，核对的版本、真实源码路径及原课程对应位置记录在：[Coding Agent开源项目源码学习案例库](../curriculum/project-source-casebook.md)。

按需匹配当前知识点，例如：**Tool Registry**优先比较Python Kimi CLI的`KimiToolset`与TypeScript Kimi Code的`IAgentToolRegistryService`；**Agent Loop**优先读Pi的`agentLoop`/ `runToolCall`；**Harness**优先读DeepSeek插件式实现；**SDK事件**先看Codex的TypeScript`Thread.runStreamed`。

案例库包含第三方/官方开源项目，**不得推断用户拥有、亲自开发或Vibe Coding生成了这些上游仓库**。它们只作为阅读参考；日后用户还可以提供自己真实Vibe Coding的项目或Fork，单独记录本人修改部分和实际知识证据。

### 其他项目后续录入规则


用户之后可随时提供多个项目；不必一次填写完整表格。每个项目可以逐步登记以下信息：

- 仓库URL或上传代码、使用的语言/框架。
- 项目在做什么；是否可访问；哪些模块已经存在。
- 哪些部分是Vibe Coding/由AI生成、哪些是自己修改过的、哪些目前不清楚（允许未知）。
- 希望借项目学习哪些概念；没有明确目标时，就匹配**当前章节**推荐最贴近的一个入口。

一个章节可对应多个项目，一个项目也可支持多个章节。**项目只作为教学案例，并不自动绑定为长期毕业项目，也不要求改写或重构所有项目。**

## 6. 实践与求职表达的边界

- **阅读理解**可以说“分析过项目的Tool Registry/Adapter/Agent Loop设计，并能解释调用链与取舍”。
- **测试验证**可说“为某个模块设计过或亲自执行了某测试”，必须有对应事实。
- **代码开发贡献**只能在自己确有修改、验证、提交等证据时描述贡献范围。
- 不因为项目由AI生成就否定其学习价值，也不把Vibe Coding项目等同于独立开发经验。
- 不把“找到类似函数”“代码能跑”当成已经彻底理解；重点是能独立解释、定位、比较及迁移。
