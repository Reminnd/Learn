# 教学运行快路径：减少内部等待，不降低教学质量

> **适用范围**：`Reminnd/Learn`的教学续学、源码对照和GitHub进度管理。本文件优化的是**取数、调度、重复判断与事务I/O**，不是教学内容长度、深度或源码引用频率。原课程、mastery、答题和安全语义均不改变。
>
> 触发读取：新的教学执行环境需要核对性能策略、诊断响应变慢，或进行教学运行时优化时。普通已恢复的教学回合**不需反复打开本文件**。

## A. 不可牺牲的教学质量

1. **不缩短常规教学回复作为提速手段**：仍然根据学习者问题提供足够的原理、Python/C++/TypeScript类比、结构化分析、真实工程示例、适用边界及必要图表。简单问题可以自然简洁，但不得为了省时删掉回答当前疑惑必需的步骤。
2. **不将真实源码引用改成仅偶尔引用**：凡以某仓库的具体函数、类、实现行为为论据，都保留仓库、文件、可直接查看的源码链接与版本/commit（能取得时）。**是否引用由内容本身决定，不受速度目标降低**。
3. **不放宽验证**：未知函数/调用路径不得猜造；涉及当前版本、实质性API变化、源码已变更或先前未核验的行为时，仍必须读真实代码或官方资料。静态类型、DI作用域、任务取消、权限、动态代码执行等易错细节不能只凭类名推断。
4. **不削弱学习验收**：一次只问一题；答案误区需纠正并复检；Mastery仍以正式章契约和已提交证据判定。未通过验证不能标已掌握，也不能把AI生成代码算作学习者手写。

## B. 同一聊天的零重复启动快路径

当本聊天**已经恢复成功**且已有当前教学知识、章节片段和session-local snapshot时：

```text
用户回答
→ 直接判断/解释（如需真实源码，优先复用本会话已核验的commit与片段）
→ 更新session-local working state与candidate checkpoint
→ 给出完整下一轮教学和一道题
→ 达到已配置的flush条件才提交GitHub
```

- 不重新执行“读取Contract→读取Skill→读取manifest→读取state→读笔记→读教材”的完整启动链。
- 不因用户只回复“A”“正确”“继续”就重新读取仓库；当前上下文足以回答时直接教学。
- 不为了“确认当前state有没有变”回查GitHub。正常buffered turn遵守manifest的`remote_reads=0`与`remote_writes=0`目标。
- 如果用户真正切换课程位置、需要最新源码、出现资料冲突或明确要求审计，才运行对应的必要远端读取。

## C. 新聊天最小恢复路径

1. 按`LEARNING_CONTINUATION_CONTRACT.md`完成**一次**bootstrap，读取manifest和committed `state.current`，遇到非空WAL优先recovery-only。
2. 已确定`note_pointer`与`chapter_file`后，可**并发读取两个不同文件的必要区段**；章节验收契约按真实教学/评定阶段读取，不为每次普通问答重复加载全部章。
3. 只加载当前教学任务需要的源码片段/示例；项目案例目录、历史笔记、所有GitHub仓库**不做每次启动的全量遍历**。
4. Bootstrap完成后将已加载文本、commit/文件SHA与本会话教学位置纳入临时working snapshot。进入同一聊天后续轮次走B节快路径。**跨新聊天不得复用未持久化的临时缓存冒充committed证据**。

## D. 源码证据与工具调度

- **证据保持可见**：当教学引用Kimi/Pi/Codex等真实函数时，给出源码链接/文件；引用不因性能策略而减少。如果本会话已核对相同**不可变commit**及同一片段，可直接复用结论和链接，无须每轮重新下载；如果依据最新`main`行为、版本变化或片段尚未核实，仍需重新验证。
- **并行仅用于相互独立的读取**：例如同一章需要的`chapter_file`与`notes.root`，已知道准确路径后可批量并发；不同仓库若都确有教学必要，可并发读取各自目标文件。**禁止将同一路径的多次写入、WAL准备/领域upsert/final-state-clear按并发执行**，依赖关系必须严格顺序。
- **一次只处理当前需要的知识点**：源码仍需完整必要调用链，但不为了讲一个函数遍历整座仓库；需要完整追踪时可以扩展读取深度，不受“最多几个文件”的机械限制。
- **重复论据不重复核对**：对同一已验证事实使用稳定源码锚点；允许教学解释更深入、引用更完整，不等于再次运行GitHub查找。
- **不凭猜测省工具**：风险较高、参数签名不确定、隐藏实现及版本变化时按正常严谨路径核对。

## E. 进度提交与异常边界

- 完全遵循manifest的`checkpoint_batching`：当前设定`max_checkpoints=3`，以及`needs_review`、小节/章节边界、Mastery、暂停、handoff等即时flush条件。**不为提速擅自提高阈值、关闭持久化或省略必须的flush**。
- 普通回合只形成candidate checkpoint；当前聊天可继续使用临时状态，未flush不得声称GitHub已保存。
- Flush时按目标文件合并多条证据；严格`prepared WAL → domain writes → final-state+clear`，依赖顺序不变；正常明确写入成功直接复用API返回SHA而不是回读一次“验证成功”。
- 出现冲突、unknown outcome、WAL恢复或掌握判定需要缺失证据时再必要刷新，严格按`shared/session-persistence.md`处理。
- 如果外部服务缓慢或失败，不用编造源码、假装保存、漏答必需问题的方式掩盖。

## F. 可检查指标（不伪造耗时提升百分比）

| 场景 | 优化后期望行为 | 保持不变 |
|---|---|---|
| 当前聊天连续回答 | 无重复bootstrap；未触发flush时学习状态GitHub读/写均为0 | 完整教学解释、一次一题与正确性 |
| 新聊天继续学习 | 一次manifest/state恢复；已知路径的必要片段可并发获取 | commited状态、异常恢复 |
| 已验证源码再次用于同一知识点 | 复用同一commit的出处与代码证据，**继续提供引用** | 准确性、版本标记、调用链 |
| 真正的新源码、版本差异 | 有依据地重新读取和追踪 | 不杜撰路径或最新行为 |
| 三次有效checkpoint/小节边界 | 原batching/WAL流程完成，合并同一文件证据 | 正式Mastery、幂等与错误恢复 |

**性能验证口径**：只能记录可实际观察的远端读取/写入次数、重复bootstrap次数、文件量及主观/实测响应时间。没有可比的真实耗时基线时不宣称“提速X%”。此策略不能授权后台异步提交或在当前回答之后才交付必须完成的工作。
